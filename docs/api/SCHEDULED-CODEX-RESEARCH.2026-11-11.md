## 四个问题的答案

| 问题 | 已建立的结论 | 仍需在选品项目证明 |
| --- | --- | --- |
| 能不能每天自动跑？ | 内置 Scheduled 支持周期执行；同聊天任务支持每日/每周接续，独立任务可每次产生新运行。[定时任务](https://learn.chatgpt.com/docs/automations) | 一次实际到点触发、工具可用和产物落盘。已有功能不等于已部署每日选品 |
| 没人发消息时怎样开始？ | 调度器使用预先保存的任务说明启动。原聊天任务复用上下文；独立任务从保存的说明开始。无需主人每天输入类目、关键词或先选中候选 | 入口读取既定研究策略、批次和未结状态；发现与研究优先级由选品规则决定，不从空白聊天猜业务规则 |
| 中断后怎样恢复？ | CLI 支持 `codex exec resume <SESSION_ID>`，可继续指定持久会话；JSONL 提供轮次成功、失败及错误事件。[非交互模式](https://learn.chatgpt.com/docs/non-interactive-mode) | 项目须读取保存的业务进度并核对原外部请求；恢复聊天历史不保证外部操作恰好执行一次 |
| 额度算在哪里？ | ChatGPT 登录使用订阅访问；API key 使用 Platform API 计费。定时触发本身不会把登录方式变成 API key。[认证说明](https://learn.chatgpt.com/docs/auth) | 在最终运行入口核验实际认证、配置、工具权限及用量口径，不能只凭开发聊天的状态推断 |

## 现成方案与选择理由

| 方案 | 适用位置 | 本次建议 |
| --- | --- | --- |
| 桌面内置 Scheduled | 本机文件、项目工具、技能和可访问的连接器；同聊天接续或独立项目运行 | 首选验证。当前宿主工具提供 heartbeat 与本地 cron；不另造基础调度循环 |
| 现成调度器调用 `codex exec` / Codex SDK | 后续确需程序控制启动、事件流和结果交接时 | 备选。CLI 已支持脚本与 scheduled jobs，SDK 已有启动/续接机制；不因“自动化”默认改用 API key。[CLI](https://learn.chatgpt.com/docs/non-interactive-mode)、[SDK](https://learn.chatgpt.com/docs/codex-sdk) |
| Web 定时任务 | 材料与工具已经在可访问的上传/连接环境中 | 不是本机项目的直接替代：不能直接使用电脑文件夹。当前宿主创建 cron 的工具仅声明 local；未验证账户的云端运行能力。[定时任务](https://learn.chatgpt.com/docs/automations) |
| 自建 App Server 客户端 | 确需自己管理认证、会话、审批和事件的产品 | 当前没有必要为每日触发先建设这一层；官方也将一般自动化引导至 SDK。[App Server](https://learn.chatgpt.com/docs/app-server) |

heartbeat 适合回到已有研究聊天；独立项目任务适合每轮从固定入口读取持久业务记录。选择不改变“每日主动发现 → 初筛/精筛 → 按确定后的规则评分排序 → 交卡审选”的主流程。开发会话不能成为唯一业务状态库。以上是候选组合，尚未选择生产任务形态或修改任何定时设置。

当前工具说明要求普通周期跟进默认使用 heartbeat；只有明确的独立项目任务或每轮新聊天需求才采用 cron。创建、修改应使用宿主原生工具。现有自动化先查重；不复用无关旧任务承载选品，也不因本次调查停启旧任务。

## 本地运行和恢复的边界

官方明确要求本地项目运行时电脑开机、应用运行、目录存在；无人值守仍受沙箱、规则及管理策略约束。网络访问和模型服务可达是在线研究的必要条件。**未找到明确文档保证休眠、离线、应用退出或忙碌期间错过的任务会如何补跑、重叠或重试，不能承诺自动补齐。** [定时任务](https://learn.chatgpt.com/docs/automations#permissions-and-security-model)

下面是本项目需要实现和验证的恢复行为，不是对 Codex 现成功能的保证：

1. 入口先读取本周期记录、规则版本和未结请求；重复唤醒不能重复提交同一操作。批次身份与实际请求、阶段、尝试身份分开。
2. 保留已完成阶段的证据和结果。会话可续接时使用保存的准确会话 ID，避免并行任务下用 `--last` 选错聊天。若要求会话恢复，不使用 `--ephemeral`。[CLI 会话恢复](https://learn.chatgpt.com/docs/non-interactive-mode#resume-a-non-interactive-session)
3. 原外部请求结果未知时先核原请求；缺原资源 ID 或不可查询则保持未知和适用预留。下一天、新会话或换月都不解除共享费用阻断。[项目接口约束](CONTRACT.draft.md#5-request-identity-recovery-and-spending-continuity)
4. 分别记录“已触发”“模型轮次结束”“业务请求核清”“卡片已保存”。进程退出码、最后一段聊天文字或一次 HTTP 成功都不能单独证明业务完成。
5. 权限、登录或额度导致无法继续时，保存具体受阻状态和可读结果；不自动切换付费 API。未被验证的补跑不能通过重做全部研究来伪装恢复。

原生任务若采用新 worktree，忽略目录中的经营证据和未结账本不会自动随 Git 出现。后续须明确同一私有状态的访问方式及写入所有权；不能复制第二份活动账本、清零预留或并发写入开发检出。

## 额度的四种口径

| 口径 | 含义 |
| --- | --- |
| Codex / ChatGPT Work 订阅用量 | 账户共享；本地与云端任务共享计划额度。每个聊天、每天的批次或新 worktree 都不会得到新额度。模型、上下文、推理及工具工作量会影响消耗，不能从 API 美元价格倒算订阅可跑多少任务。[用量说明](https://learn.chatgpt.com/docs/pricing) |
| ChatGPT 侧额外 credits | 包含额度耗尽后，可用 credits 可能支持继续工作。这和 API Platform 余额不同；不配 API key 并不等于已经建立“只用包含额度”的硬停止保证。[credits 说明](https://learn.chatgpt.com/docs/pricing#what-are-tokens-and-credits) |
| OpenAI API 用量与赠送额度 | 仅所选辅助 API 使用单独计费口径。官方注明赠送 API credits 不增加已登录 Codex 额度，而且不覆盖通过 API key 使用 Codex；实际赠额资格和余额本次未查询。[赠送额度边界](https://developers.openai.com/api/docs/guides/chatgpt-api-credits) |
| 卖家精灵、SIF 等外部数据 | 按各服务的权限与额度单独管理；Codex 订阅不能证明这些调用免费或已获准。具体费用由选定提供方证据核对 |

本机当前 shell 未发现会覆盖该 CLI 路径的 `CODEX_API_KEY`、`OPENAI_API_KEY`、`CODEX_ACCESS_TOKEN` 或联邦认证环境变量；未修改配置，也没有读取/复制密钥文件。原生只读用量接口返回账户共享的窗口及 credits 信息，不能据此预测每日选品容量或证明另一个执行环境的计费归属。

后续若要求严格限于订阅包含额度，须验证耗尽前后实际入口的停止行为、额外 credits 控制和并发用量影响。官方称达到限额时正在进行的轮次可能继续至完成，受 fair-use 限制；因此轮次前的额度快照不是本次运行的硬额度保留。[限额行为](https://learn.chatgpt.com/docs/pricing#what-happens-when-you-hit-usage-limits)

## 与选品开发的接入约定

建议第一条可验收切片为：**现成周期入口 → 项目读取策略与批次 → 合成发现/研究数据 → 已确认规则或明确待定状态 → 保存可读卡片**。该切片先证明技术链路，不能拿合成卡片当真实选品效果，也不能用默认评分填补未定业务规则。

后续验收至少区分：

- 无人发送当天新消息且没有人工种子/点选时，实际到点启动，并读取正确项目、身份、策略和工具。
- 重复触发、相邻批次重叠、阶段中断、跨日/跨月未知请求时，既不串候选版本，也不重复收费提交；已有结果可读。
- 应用退出、主机休眠/离线、登录失效或额度不可用时，记录可核对的结果；对补跑方式依据实测确定，不提前承诺。
- 同一实际入口的认证与用量归属能核对；模型成功、第三方数据调用、卡片持久化和业务质量分别验收。

这份调查授权不包含新扫描、收费模型/业务调用、调度启停、凭据或账本变更。本机帮助命令返回成功但伴随临时目录/PATH alias 的权限警告，未修复主机，也未将帮助成功视为运行验收。
